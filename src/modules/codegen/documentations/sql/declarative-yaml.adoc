The SQL Framework supports a declarative YAML form for the connector manifest, schema documents, and
operation documents, in addition to Groovy scripts.

== Connector manifest

Exactly one of `connector.manifest.json`, `connector.manifest.yaml`, `connector.manifest.yml` is
present on the classpath. It lists script resources; Groovy and YAML entries may be mixed freely,
and an entry may be disabled without removing it:

[source,yaml]
----
connector:
  schema:
    - script: /schema/customize.groovy
    - script: /schema/persons.native.schema.yaml
  operation:
    - script: /handlers/user_ops.groovy
    - script: /handlers/employee.op.yaml
      disabled: true
----

If a manifest entry references a `.groovy` resource that is not bundled, the loader falls back to a
`.yaml`/`.yml` resource with the same base name, so a script can migrate to YAML incrementally
without changing the manifest. An empty or absent `operation` list is a normal, fully working
configuration: create, update, delete and search all work with zero operation script once the
object class has a SQL-backed `__UID__` mapping.

== Schema documents

A schema document declares one or more object classes under a top-level `objectClasses` map (a
single file may describe several classes; files naming the same class merge, and YAML schema
documents bind into the same live schema builder as Groovy ones, merging with auto-discovered
columns exactly the same way):

[source,yaml]
----
objectClasses:
  Person:
    sql:
      table: app_user
      schema: public
    description: Application user
    embedded: false
    readOnly: false
    onlyExplicitlyListed: false
    connId:
      UID: user_id
    attributes:
      user_id:
        connId:
          name: __UID__
        sql:
          type: INT
          primaryKey: true
          autoIncrement: true
      user_name:
        connId:
          name: __NAME__
      user_email:
        connId:
          name: emailAddress
        sql:
          notNull: true
          unique: true
      loginCount: {}
    references:
      manager:
        objectClass: Person
        subtype: reportsTo
        role: SUBJECT
----

Structure:

[cols="1,3", options="header"]
|===
|Key |Description

|`sql.table` / `sql.schema`
|Physical table name and optional schema qualifier.

|`description`
|Human-readable description of the object class.

|`embedded`
|Marks the class as an embedded/child object class rather than a standalone one.

|`readOnly`
|Single-key shortcut equivalent to disabling `create`, `update` and `delete` individually for this class.

|`onlyExplicitlyListed`
|When true, only the columns declared under `attributes` are exposed; auto-discovered columns not listed here are dropped.

|`connId`
|Object-class-level ConnID alias map (equivalent of the Groovy `connIdAttribute(...)` call), e.g. `connId: {UID: user_id}`.

|`attributes`
|Map of `column name -> attribute definition`. Full per-attribute flag set: `description`, `required`, `multiValued`, `creatable`, `updateable` (alias `updatable`), `readable`, `returnedByDefault`, `emulated`, `complexType`; `connId: {name, type}` (including `+++__UID__+++`/`+++__NAME__+++`); `sql: {name/column, type, notNull, unique, primaryKey, autoIncrement}`. An empty map (`{}`) or a bare `attributeName:` declares the attribute without renaming.

|`references`
|Map of `references.<name>`: `objectClass`, `subtype`, `role` (`SUBJECT`/`OBJECT`) - the YAML equivalent of the Groovy `reference(name) { objectClass(); subtype(); role() }` block, used for many-to-many/junction relationship attributes.
|===

== Operation documents

`create`, `update`, `delete` are configured per object class under the same `objectClasses` root:

[source,yaml]
----
objectClasses:
  Employee:
    create:
      enabled: true
    update:
      enabled: true
    delete:
      enabled: false
----

`enabled: false` turns the operation off entirely - this is the smallest YAML needed to disable one
operation while leaving the others on framework defaults. An object class needing no create/update/
delete customization needs no such key at all: basic create, update and delete all work with zero
operation script once the class has a SQL-backed `__UID__` mapping, and the framework builds the
statement from the native schema mapping. When a class has related-table (child/junction) attributes,
create/update/delete already extend to those child rows in the same transaction as the parent
operation - see relationships.adoc/related-table-writes.adoc; there is no separate configuration key
for this, in Groovy or YAML.

`search` has no declarative-YAML operation key today - see the capability boundary below.

== Capability boundary: Groovy is required for

* Custom search queries (`search { sql { custom { emptyFilterSupported; query { q -> ... } } } }`) -
  full QueryDSL SELECT/FROM/WHERE/ORDER BY, joins, computed columns. No YAML form exists for this.
* Refining the built-in search WHERE clause with a fixed extra predicate
  (`search { sql { builtIn { where { e -> ... } } } }`) - documented only as Groovy.
* The `additionalColumns() { column("other_col") }` hook for composite-UID extra physical columns.
* Resource/attribute-level custom mapping rules (`SqlSchemaTranslator.addResourceRule(...)`,
  `addAttributeRule(...)`) and fully custom operation registration - Java/Groovy extension points
  below the declarative form entirely.
* Cross-script helper `def` functions shared between a session's Groovy scripts - a Groovy-only
  convenience with no YAML analog.

== Preview / not yet functional - do not generate as working behavior

* Incremental sync (LiveSync) is not available for SQL Framework connectors - there is no `sync {}`
  DSL in Groovy or YAML, and the operation is not registered on the connector. Do not configure
  midPoint incremental sync for a SQL Framework connector; use full sync (search-based) instead.
* Scripted relationship override: the `relationship {}` function in schema scripts is a stub today.
  Relationship detection is entirely FK-constraint/naming-convention driven; there is no working
  scripted override in Groovy or YAML.
* Filtering through a detected relationship (querying parent rows by a child/junction-table
  attribute) is not part of the built-in filter translation - only direct parent-object-class
  attributes are filterable via the built-in search.

== Validation

Every YAML document here is exactly one document, with a mapping root, no duplicate keys, and only
the documented keys and strict value types at every configuration level - an unrecognized key fails validation rather than
being silently ignored. Object-class and attribute (column) names are always arbitrary.
