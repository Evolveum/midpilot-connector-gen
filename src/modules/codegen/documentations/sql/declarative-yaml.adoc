= Declarative YAML

The connector supports a declarative YAML form for the connector manifest, schema definitions, and operation handlers, in addition to Groovy scripts.

YAML documents and Groovy scripts are two front-ends over the *same* builders — a YAML document drives the same live builders the Groovy DSL does, so both forms can be mixed per connector.

IMPORTANT: Use Groovy scripts for anything requiring scripted behavior — custom search queries, `where` predicates, attribute resolvers. YAML covers declarative table/attribute mapping and operation control. This page and xref:native-schema.adoc[schema customization] describe the same schema customization — the YAML form is a declarative subset of the Groovy DSL.

== YAML connector manifest

The connector manifest may be named `connector.manifest.json`, `connector.manifest.yaml` or `connector.manifest.yml` — exactly one of the three may be present on the classpath of the connector bundle (the bundle JAR together with the JARs in its `lib/` directory; see xref:custom-connector.adoc#_option_1_manifest_based_connector_no_java[bundle layout]).

[source,yaml]
----
connector:
  schema: <1>
    - script: /schema/customize.groovy
    - script: /schema/persons.native.schema.yaml
  operation: <2>
    - script: /handlers/user_ops.groovy
    - script: /handlers/employee.op.yaml
----
<1> List of schema script resources, loaded during initialization. Groovy and YAML schema documents can be mixed.
<2> List of operation handler script resources. Groovy and YAML operation documents can be mixed.

A script entry may carry `disabled: true` — the script is skipped in both real loading and script validation, as if it were not bundled at all.

Paths starting with `/` are resolved as classpath resources from the root of the classpath.

== Native YAML schema documents

A schema document named `*.native.schema.yaml` is a flat YAML description of object classes under the `objectClasses` root (one entry per object class; a file may describe several classes).

[source,yaml]
----
# /schema/person.native.schema.yaml
objectClasses:
  Person:
    sql:
      table: app_user
    readOnly: true
    attributes:
      user_id:
        connId:
          name: __UID__
        sql:
          type: INT
          primaryKey: true
      user_name:
        connId:
          name: __NAME__
        sql:
          type: VARCHAR(255)
          notNull: true
      user_email:
        connId:
          name: emailAddress
        sql:
          type: VARCHAR(255)
      loginCount:
        sql:
          type: INT
----

Structure:

`objectClasses.<name>`::
  The ConnId object class name (the counterpart of `objectClass("...") { ... }`)

`description` / `embedded`::
  The corresponding object-class flags (see xref:native-schema.adoc[])

`readOnly`::
  The object class is read-only; create, update, and delete are disabled automatically

`onlyExplicitlyListed`::
  Only the explicitly listed attributes are considered (all other discovered columns are ignored)

`connId` (object-class level)::
  Built-in attribute alias map, e.g. `connId: { UID: user_id }` binds `__UID__` to the `user_id` attribute

`sql: { table, schema }`::
  The SQL table name (defaults to the object class name) and optional SQL schema qualifier

`attributes.<name>`::
  One attribute — the regular attribute settings (`description`, `required`, `multiValued`, `creatable`, `updateable`, `readable`, `returnedByDefault`, `emulated`, `complexType`), the `connId: { name, type }` mapping (including the `__UID__` / `__NAME__` built-ins), the inherited `json: { name, type, openApiFormat, path }` block (the `path` is an attribute-path string such as `$.name.first`, default basic JSONPath — or an explicit `{ type: JSON_POINTER, value: /name/first }` mapping), and the `sql` block below. An empty value (`{}`) declares the attribute without renaming.

`references.<name>`::
  Map of `attribute name → reference attribute definition`, with `objectClass`, `subtype`, `role` (see xref:native-schema.adoc[reference attributes])

Attribute-level `sql` keys:

`name`::
  The SQL column when it differs from the attribute name

`type`::
  The SQL column type — matched exactly (case-insensitive) against the built-in type names and the common database-specific aliases: `INT`/`INT4`/`INTEGER`, `INT2`/`SMALLINT`, `INT8`/`BIGINT`, `TINYINT`, `MEDIUMINT`, `SERIAL`/`SERIAL4`, `SERIAL2`/`SMALLSERIAL`, `SERIAL8`/`BIGSERIAL`, `IDENTITY` (integers); `DEC`/`DECIMAL`, `NUMERIC`/`NUMBER`, `MONEY`/`SMALLMONEY` (exact numerics); `FLOAT`/`FLOAT4`/`REAL`, `FLOAT8`/`DOUBLE`/`DOUBLE PRECISION` (approximate numerics); `BOOLEAN`/`BOOL`; `BIT`/`VARBIT`; `DATE`; `TIME`/`TIME WITH TIME ZONE`; `TIMESTAMP`/`DATETIME`/`TIMESTAMP WITHOUT TIME ZONE`, `TIMESTAMP WITH TIME ZONE`/`TIMESTAMPTZ`; `VARCHAR`/`VARCHAR2`/`CHAR`/`CHARACTER`/`CHARACTER VARYING`/`CHAR VARYING`/`NCHAR`/`NVARCHAR`/`NVARCHAR2`/`NCHAR VARYING`/`NATIONAL CHARACTER`/`LONG VARCHAR`/`LONGNVARCHAR`/`UUID` (characters); `BLOB`/`BINARY`/`VARBINARY`/`LONGVARBINARY`/`BINARY VARYING`/`BYTEA`/`RAW`/`LONG RAW`/`TINYBLOB`/`MEDIUMBLOB`/`LONGBLOB` (binary); `CLOB`/`NCLOB`/`NTEXT`/`TEXT`/`TINYTEXT`/`MEDIUMTEXT`/`LONGTEXT`/`XML`/`JSON` (large characters). A size/precision in parentheses is accepted but ignored (the type specifications are size-agnostic, like the Groovy `type VARCHAR(n)` constants) — e.g. `VARCHAR(100)`, `NUMBER(10, 2)`, `TIMESTAMP(6)`. An unrecognized name fails at schema evaluation with `Unknown SQL type '…'` (there is no silent fallback)

`notNull`::
  The column is not nullable

`unique`::
  The column is unique

`primaryKey`::
  The column is part of the primary key

`autoIncrement`::
  The column is auto-incremented

YAML schema documents bind directly into the same live schema builder as Groovy scripts, so they merge with auto-discovered columns exactly like xref:native-schema.adoc[Groovy customizations] do — including correlation with discovery and the built-in mapping rules.

Yes — Groovy and YAML customizations can target the same table (object class): both are applied to the same builder and are merged. The limit is that a property declared explicitly in *both* forms with *different* values is a conflict and fails at script evaluation — declare each property in exactly one place. A repeated declaration of the *same* value is tolerated.

Parsing is strict: a file must contain exactly one document, and unknown keys fail fast.

== Operation documents

An operation document covers one or more of `create`, `update`, or `delete` per object class, under the same `objectClasses` root:

[source,yaml]
----
# /handlers/employee.op.yaml
objectClasses:
  Employee:
    create:
      enabled: false
----

`create: { enabled }` / `update: { enabled }` / `delete: { enabled }`::
  Enables or disables the operation (e.g. `enabled: false` ≙ `disableCreate()`); `readOnly: true` on the schema disables all three automatically

Search works out of the box for discovered tables; Groovy remains the front-end for scripted search behavior (custom query implementations, `where` predicates — see xref:search.adoc[search] and xref:custom-search.adoc[custom search]).

== Groovy to YAML fallback

If a **schema** manifest entry references a `.groovy` resource that is not bundled, the loader transparently falls back to a `.yaml`/`.yml` resource with the same base name (operation scripts do **not** fall back — a missing `.groovy` is skipped):

[source,yaml]
----
connector:
  schema:
    - script: /schema/users.groovy   # resolves to /schema/users.yaml when only the YAML file is bundled
----

This makes it possible to migrate a script to YAML incrementally without changing the manifest.

The granularity of combining the two forms is per script resource, per object class, per attribute, and per operation — the manifest lists `.groovy` and `.yaml` resources side by side, and each is applied to the same builder. The limit is the one described above: do not declare the same property explicitly in both forms with *different* values (a table and attributes in YAML plus a search customization in Groovy is fine; the same table property in both is not).
