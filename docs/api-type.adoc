= API type (REST / SCIM / SQL)
:toc: left

link:index.adoc[← Documentation index]

`apiType` is the single most important piece of session metadata: it decides
which protocol-specific extractors and prompt families the
link:pipeline/digester.adoc[digester] and link:pipeline/codegen.adoc[codegen]
stages use. Supported values (`ApiType` in `src/common/enums.py`):

* `rest` — generic REST/OpenAPI provisioning API,
* `scim` — SCIM 1.1/2.0 provisioning,
* `sql` — direct database (SQL schema based) integration.

== How it is detected

The digester *metadata* step (`POST /api/digester/{sessionId}/metadata`)
detects the apiType by combining several independent signals
(`src/modules/digester/extractors/apitype/`):

[cols="1,3", options="header"]
|===
| Signal | How it works

| `documentation`
| Per-chunk LLM extraction from the stored documentation.

| `scim_cloud`
| Lookup of the application name in the public
  https://scim.cloud[scim.cloud] SCIM implementations registry (fuzzy match,
  cached, SCIM only).

| `knowledge_of_llm`
| Documentation-free question to the LLM whether the application is known to
  support SCIM / REST provisioning.

| `web_search`
| Web search for SCIM / REST support plus an LLM assessment of the results
  (fetches result pages by default — the most expensive signal).
|===

Each signal can be toggled and tuned via `+DIGESTER__*+` settings
(`scim_cloud_enabled`, `apitype_scim_knowledge_enabled`,
`apitype_scim_web_search_enabled`, `apitype_rest_*`, thresholds and query
templates — see `src/config/digester.py`).

The merged result is stored in the session `infoMetadata` as an `apiType`
*list* (an application can expose several protocols), together with a
per-protocol *availability advisory* (`available` / `paid` / `unknown`) that
warns when a protocol exists but is gated behind a paid or enterprise plan.

== How it is resolved and overridden

When a digester or codegen job needs a single protocol, it resolves it via
`src/common/utils/session_info_metadata.py`:

1. If the request carries an explicit `apiType` *query parameter*
   (available on `POST /api/digester/{sessionId}/classes` and on every
   codegen generation endpoint), that value wins.
2. Otherwise the stored `apiType` list from the session metadata is used.
3. If nothing is stored, the protocol *silently defaults to `rest`*.

== Pitfalls

IMPORTANT: Run metadata extraction *before* object classes, endpoints,
attributes, or any codegen. Without it there is no stored apiType and
everything falls back to REST — for a SCIM or SQL target this means wrong
extractors, wrong prompts, and unusable output, with no error raised.

IMPORTANT: When the target exposes several protocols (detection stored e.g.
both `rest` and `scim`), decide which connector you want and pass the
explicit `apiType=` override consistently on *all* extraction and generation
requests. Mixing protocols mid-pipeline (classes extracted as SCIM, code
generated as REST) produces inconsistent results.

WARNING: The `integrationType` field of the
link:pipeline/discovery.adoc[discovery] request is *not* the apiType — it only
biases the documentation search. Do not expect it to configure the digester
or codegen.

NOTE: Check the availability advisory in the metadata output: a detected
protocol marked `paid` may not be usable on the customer's actual plan even
though the connector can be generated.

NOTE: The base API URL and connection target are also read per-protocol from
the metadata. If you override apiType, the corresponding protocol block must
exist in the metadata (or be filled in manually via
`PUT /api/digester/{sessionId}/metadata`).
