== Sessions

All work happens inside a *session* — a workspace identified by a UUID that
accumulates everything the pipeline produces: uploaded/scraped documentation,
detected metadata, extracted object classes, generated code. A session must
exist before any pipeline endpoint is called.

[cols="2,3", options="header"]
|===
| Endpoint | Purpose

| `POST /api/session`
| Create a session (server-generated ID).

| `POST /api/session/{sessionId}`
| Create a session with a caller-provided ID (409 if it exists).

| `GET /api/session/{sessionId}`
| Session summary. `HEAD` variant checks existence.

| `GET /api/session/{sessionId}/jobs`
| List all jobs belonging to the session. Running rows include worker,
  heartbeat, claim expiry, and attempt metadata for operational visibility.

| `DELETE /api/session/{sessionId}`
| Delete the session and all associated data.
|===

=== Documentation in a session

Documentation can enter a session two ways: via the
link:pipeline/scrape.adoc[scrape stage], or by direct upload:

[cols="2,3", options="header"]
|===
| Endpoint | Purpose

| `POST /api/session/{sessionId}/documentation`
| Upload a file; it is chunked and processed in a background job (LLM-based
  for normal documents, deterministic for conndev exports).

| `PUT /api/session/{sessionId}/documentation`
| Replace *all* documentation in the session with one uploaded file.

| `PUT /api/session/{sessionId}/documentation/{docId}`
| Import already-processed documentation (chunks as JSON) — no LLM involved.

| `GET /api/session/{sessionId}/documentation`
| Export all documentation grouped by document.

| `GET /api/session/{sessionId}/documentation/status`
| Status of upload processing jobs.

| `DELETE .../documentation`, `DELETE .../documentation/{docId}`
| Remove documentation.
|===

SQL inputs can be uploaded directly as `.sql`/SQL media types, as a JSON table
list (prefer `application/sql+json` so schema-preserving chunking is selected),
or as a midPoint conndev export (`.conndev`,
`application/conndev+json`, or
`application/com.evolveum.conndev+json`). See
link:pipeline/digester.adoc#sql-schema-sources[SQL sources of schema].

NOTE: Normal uploads go through the same chunking and LLM chunk-processing as
scraped documentation, so the digester treats both sources identically.
Conndev exports are preserved and classified from their binding
deterministically; they do not call the chunk-processing LLM. The application
name/version for normal processing is taken from the session's `discoveryInput`
or `scrapeInput` — run (or at least record) those inputs first for best results.

== The asynchronous job pattern

Every expensive operation follows the same contract:

1. `POST` to the operation endpoint *enqueues a background job* and returns
   immediately with a `jobId`.
2. `GET` on the same path returns the job status
   (`queued` / `running` / `finished` / `failed`), progress stages, and — once
   finished — the result.
3. The `jobId` query parameter on `GET` is optional: each `POST` also persists
   the job pointer into the session (e.g. `discoveryJobId`,
   `objectClassesJobId`), so the status endpoint finds the latest job by
   itself.
4. Many resources also support `PUT` to overwrite the stored result manually
   (e.g. correcting an extracted object class before running codegen).

Job statuses and progress stages are defined centrally in
`src/shared/enums.py` (`JobStatus`, `JobStage`).

== Durable multi-worker execution

The job row contains a versioned execution payload, ownership token, attempt
counter, heartbeat, and claim expiry. Every enabled FastAPI process runs a
consumer which claims work with PostgreSQL `FOR UPDATE SKIP LOCKED`; two
workers therefore cannot receive the same execution token.

While a job runs, its worker refreshes the claim. A hard-stopped process leaves
the job in `running`; after the claim expires another process can reclaim it.
All final state and session-result writes are fenced by the execution token,
so the old process cannot overwrite the new worker even if it resumes late.
Graceful shutdown returns interrupted work directly to `queued`.

=== Deployment shapes

The consumer runs in one of two shapes, both of which claim from the same
queue and need no coordination beyond PostgreSQL.

*Embedded* (default). Every FastAPI process started with `+JOBS__ENABLED=true+`
runs a consumer, so a single `python server.py` both serves requests and drains
the queue. Throughput is raised with `+APP__WORKERS+` and
`+JOBS__MAX_CONCURRENT_JOBS+`.

*Standalone.* For scaling the API and the queue independently, run API
processes with `+JOBS__ENABLED=false+` and consumers from the worker entry
point:

[source,shell]
----
python -m src.jobs.runtime
----

It applies the same per-process concurrency, claim timeout, heartbeat, CPU-pool
and shutdown settings as the embedded consumer, but starts no HTTP server. It
does not read `+JOBS__ENABLED+` - a process started this way is always a
consumer. Because it builds no FastAPI application it opens no listening port
and stays roughly 65 MB smaller than an API process, which also keeps the API
from being reachable on hosts that are only meant to do background work.

WARNING: Every process opens its own database pool, so scaling out multiplies
the connection count. Eleven processes on the default pool settings can exceed
PostgreSQL's own default `max_connections` of 100 and fail with
`sorry, too many clients already`. Size `+DATABASE__POOL_SIZE+` and
`+DATABASE__MAX_OVERFLOW+` together with the server limit - see
link:configuration.adoc[Configuration].

Execution is *at least once*: if a process dies after an external LLM provider
accepted a request but before the result was persisted, the reclaimed attempt
may repeat that LLM call. Database side effects are fenced/idempotent, but an
exactly-once guarantee cannot be imposed on an external API across an
ambiguous network/process failure.

Documentation dependencies are part of the PostgreSQL claim predicate. A
digester job stays queued without occupying a concurrency slot while scrape or
upload processing is active in the same session. The dependency timeout is an
enqueue-time budget measured from durable job creation, rather than from the
later worker claim. If it expires while a producer is still unfinished, the
worker logs a warning and records the degraded continuation in the job's
non-fatal errors before claiming it. Uploaded source bytes are
stored in the shared `job_artifacts` table (`BYTEA`) and the small versioned
execution payload contains only a named reference. Artifacts and the execution
payload are cleared on finish/failure. Deployments with very large upload
retention or throughput can replace this table with shared object storage
without changing the worker-call contract.

The job and its `{key}JobId` session pointer are inserted in the same request
transaction. Database dependencies use FastAPI function scope: response-model
validation finishes first, the transaction then commits, and only afterwards
is the enqueue response sent. A consumer or an immediate status request sees
neither record until both commit, and once the client receives a successful
enqueue response it can poll without a transient `job_not_found`. An exception
or commit failure rolls the entire request transaction back. Result persistence
checks that the pointer still references
the completing job, preventing an older parallel job from overwriting a newer
result. The older computation remains a finished historical job, but its
`errors` list explicitly records that the result was not published to the
session.

Run `uv run alembic upgrade head` before starting the updated application.
Migration `007` marks pre-migration queued/running jobs as failed because they
do not contain a resumable execution payload. The same migration adds
idempotency keys for documentation chunks.

== Result caching and `skipCache`

Discovery, scrape, and digester jobs cache results by *normalized input*: if
the same input was already processed in the same session or API-key tenant
within a configured time window, the stored result is reused instead of
re-running the LLM work. With authentication disabled, ownerless sessions form
one cache tenant; production deployments should enable API-key authentication.

* The windows are configured per module:
  `+SEARCH__DISCOVERY_INPUT_CHECK_INTERVAL+`,
  `+SCRAPE_AND_PROCESS__SCRAPE_INPUT_CHECK_INTERVAL+`,
  `+DIGESTER__DIGESTER_INPUT_CHECK_INTERVAL+` (all default to 4 weeks).
* Every such endpoint accepts `skipCache=true` (query parameter or request
  field) to force a fresh run.

IMPORTANT: When testing prompt or extraction changes, pass `skipCache=true` —
otherwise you may be looking at a weeks-old cached result and wrongly conclude
your change had no effect.
