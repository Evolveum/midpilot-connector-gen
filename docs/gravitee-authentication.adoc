= Gravitee authentication and session isolation
:toc:

== Responsibility and trust boundary

Gravitee owns API-key issuance, subscriptions, expiry and revocation. FastAPI
accepts the gateway-validated `X-Gravitee-Api-Key` header and hashes its exact
value with SHA-256. `sessions.owner_key_hash` stores this fingerprint, never the
raw key. No local registration, master key or `/api/v1/apiKeys` endpoint exists.
Use random, high-entropy keys generated by Gravitee.

The fingerprint identifies the owner of a session and scopes cross-session job
result reuse. Different keys cannot access each other's sessions or cached
results. A rotated key has a different identity: old sessions do not transfer.
Keys shared by clients also share ownership. Session IDs are not credentials.
Revocation affects subsequent requests once enforced by the gateway; it does
not cancel background jobs already accepted or delete stored sessions.

IMPORTANT: The backend does not authenticate the sender of this header. In
`prod` mode, deployment MUST prevent consumers from reaching backend API
routes except through the authenticating gateway. A directly reachable backend
would accept any well-formed header as an identity. A VPN or Kubernetes
ClusterIP alone does not establish this boundary. Use gateway-only network
access and, where required, an authenticated connection such as mTLS at the
service proxy. Do not use forwarded IP headers as proof of gateway identity.

== Application configuration

[source,dotenv]
----
AUTH__MODE=prod
----

This is the default. Missing, empty, duplicate, comma-separated or whitespace-
containing key headers are rejected with HTTP 401. No database lookup or remote
introspection call is made to validate a key. Unknown mode values fail startup.
The previous `AUTH__API_KEY_REQUIRED` and `AUTH__MASTER_API_KEY` settings no longer
control authentication; remove them from every deployment and local env file.
`X-API-Key` and the `api-key` query parameter are not identity sources.

For local work without a gateway, explicitly configure:

[source,dotenv]
----
AUTH__MODE=dev
----

Development mode ignores keys, creates ownerless sessions, and bypasses session
ownership checks. Ownerless sessions share reusable results only with other
ownerless sessions. Use a separate disposable database for this mode; it is not
an administrator mode for a shared deployment. After switching to `prod`,
ownerless sessions are inaccessible. There is no master-key bypass.

The backend `/health`, `/docs`, `/redoc` and `/openapi.json` routes remain public
at the application layer. Network exposure and gateway policies must be chosen
explicitly; gateway plans can still protect these routes when proxied.

== Administrator: configure Gravitee

. Create an HTTP Proxy API. For Docker Desktop with FastAPI running on the
host's port 8090, use context path `/midpilot` and endpoint
`http://host.docker.internal:8090`. For Kubernetes, use the service address
reachable from the gateway. Verify prefix handling: `/midpilot/api/v1/session`
must reach backend `/api/v1/session`.
. Publish an API Key plan and enable *Propagate API Key to upstream API*.
Remove any Keyless plan and other routes that bypass authentication.
. Keep the gateway's API-key header configured as `X-Gravitee-Api-Key`.
Accept consumer credentials in this header only. Disable query-parameter API
keys in the gateway configuration (`policy.api-key.param` set to an empty
string), and reject duplicate/comma-joined credential headers. Ensure the
forwarded value is exactly the value validated by the selected plan.
. Create separate applications/subscriptions and generate two distinct keys
for isolation testing. Keys need no registration in FastAPI.
. Deploy/start the API and wait for gateway synchronization. After revocation,
verify rejection through the gateway rather than assuming immediate propagation.
. Exclude API-key headers and credentials from gateway request capture, access
logs, traces and support exports. Send hosted traffic over TLS.
. Enforce the gateway-only backend network boundary before shared/public use.
The local host-accessible setup below is for single-developer testing only.

See the official
https://documentation.gravitee.io/apim/create-and-configure-apis/apply-policies/policy-reference/api-key[API Key policy]
and https://documentation.gravitee.io/apim/configure-and-manage-the-platform/gravitee-gateway[gateway configuration].
Names in the Console vary by APIM version. Coordinate gateway-wide configuration
changes with the infrastructure owner.

== User: local verification

Restart FastAPI with `AUTH__MODE=prod` and the updated database schema.
Use two newly generated Gravitee subscription keys, not the former master key.
In zsh, enter the secrets without including them in shell history:

[source,shell]
----
read -rs 'KEY_A?Gravitee key A: '
echo
read -rs 'KEY_B?Gravitee key B: '
echo
----

Create a session as A:

[source,shell]
----
curl -i -X POST http://localhost:8082/midpilot/api/v1/session \
  -H "X-Gravitee-Api-Key: $KEY_A"
----

Expect HTTP 201. Copy the returned `sessionId` into `SESSION_A`, then read it:

[source,shell]
----
SESSION_A='<returned-sessionId>'
curl -i "http://localhost:8082/midpilot/api/v1/session/$SESSION_A" \
  -H "X-Gravitee-Api-Key: $KEY_A"
curl -i "http://localhost:8082/midpilot/api/v1/session/$SESSION_A" \
  -H "X-Gravitee-Api-Key: $KEY_B"
----

Expect 200 for A and 404 with `error.code=session_not_found` for B. Repeat in
reverse after creating a session with B. Only one header is needed; remove the
`X-API-Key` header from previous dual-authentication examples.

Call through the gateway with no key, an unknown key and a revoked key: each
must be rejected before reaching FastAPI. A 401 from FastAPI about a missing
header usually means propagation is disabled or the header was renamed.
A gateway 502/504 usually means the endpoint is unreachable or timed out.

Before hosting, additionally verify that direct backend access from a consumer
network is blocked, that duplicate credentials cannot select different keys
at the gateway and backend, and that a key rotation cannot read old sessions.
Run `uv run poe test test/unit/auth` and the PostgreSQL ownership/reuse tests
with `TEST_DATABASE_URL` pointing to a disposable test database. These tests do
not replace a live gateway revocation and network-boundary test.

== Schema upgrade

The pre-production Alembic revisions 006 and 008 now describe fingerprint-based
ownership without a local key registry. Existing databases need the one-time schema cleanup documented below;
`alembic upgrade head` alone does not change an already-applied revision.
The cleanup removes old keys and ownership links without transferring them.
Existing sessions become ownerless and are inaccessible in `prod`; other data
is retained. Fresh databases use `uv run alembic upgrade head`.
See `docs/milestone-notes.adoc`, entry
`2026-09-22 Delegate API keys to Gravitee and isolate sessions by fingerprint`,
for exact cleanup, rollback and validation steps.
