= Scrape
:toc: left

link:index.adoc[← Pipeline overview] | link:../index.adoc[Documentation index]

Scrape crawls documentation pages starting from a set of URLs, follows
relevant links, and converts the content into processed documentation chunks
stored in the session — the input for the link:digester.adoc[digester].

Module: `src/modules/scrape/` (crawling built on crawl4ai + Playwright via
`src/integrations/web/`).

== Endpoints

[cols="2,3", options="header"]
|===
| Endpoint | Purpose

| `POST /api/scrape/{sessionId}/scrape`
| Enqueue a scrape job. Body: `ScrapeRequest` — `starterLinks` (required),
  `applicationName` (required), `applicationVersion`, `skipCache`.

| `GET /api/scrape/{sessionId}/scrape`
| Poll the job status; progress is reported per scraper iteration.
|===

== Process

1. *Crawl* the starter links (typically the link:discovery.adoc[discovery]
   output). A URL served as JSON, YAML or plain text is downloaded as a data
   file (up to `+SCRAPE_AND_PROCESS__MAX_DATA_DOCUMENTATION_BYTES+`); any other
   page is rendered with crawl4ai/Playwright. Starter links are fetched even
   when they match a forbidden URL part.
2. *Keep only documentation.*
   * A rendered page is read as the markdown of its main content: the first of
     `+SCRAPE_AND_PROCESS__MAIN_CONTENT_SELECTORS+` (`article`, `main`,
     `[role=main]`) that matches one element holding most of the page text,
     otherwise the page body without header, footer and sidebars. Navigation is
     removed; tables and code samples are kept. A page without main content is
     not saved, but its links are still followed.
   * Each page, and each plain-text data file such as a raw markdown file, is
     *assessed* by an LLM before it is saved (`Scrape:Pages:Assess`, up to
     `+SCRAPE_AND_PROCESS__ASSESSMENT_CONTENT_TOKENS+` of its content): whether
     a connector developer needs it, its role (API reference, authentication,
     navigation, marketing, …), the topics it covers, the object classes it
     mentions, and whether it documents the application and the target version.
     A product or version mismatch counts only with a quote from the page as
     evidence; without one it is `unclear`. The version is assessed only when
     the scrape targets a concrete version (see the note below).
   * A page is saved when the assessment keeps it and it does not document
     another product; the links of a page of another product are not followed.
     A page of another version is saved and its links are followed, with the
     mismatch recorded in its chunk metadata: vendors often publish only their
     latest documentation (Nextcloud only `/server/stable/`), which is then the
     best there is. A starter link is always saved; a product or version
     mismatch on one is recorded in the job `errors`. When the assessment fails,
     the page is saved without it and the failure is recorded in the job
     `errors`; an unreachable LLM fails the job.
   * A data file is saved when it is an API description (OpenAPI 3, Swagger 2,
     SCIM schemas or resource types, JSON Schema); API descriptions are
     validated, not assessed. Other JSON/YAML (`package.json`, translation
     bundles) is saved only when it is a starter link. A copy of an API
     description the job already saved (the same specification as JSON and
     YAML, or served by another instance that lists itself in `servers` or
     `host`) is not saved again, unless it is a starter link.
3. *Fetch referenced specifications.* A page built from an API description
   (Swagger UI including `swagger-initializer.js` and `configUrl`, Redoc,
   Stoplight Elements, RapiDoc, Scalar), a `<link rel="alternate">` or a
   JSON/YAML download link to one, or a link whose URL names one
   (`openapi.json`, `swagger.yaml`, `/v3/api-docs`) leads to the document
   itself, fetched in the same iteration and never crawled further. GitHub file
   pages are read as raw files. Only URLs in the crawl scope and raw GitHub
   files are fetched, at most `+SCRAPE_AND_PROCESS__MAX_SPEC_URLS_PER_PAGE+` per
   page, and only a recognized API description is saved.
4. *Collect links* from the pages whose links are followed: every link of the
   page, navigation included, made absolute and stripped of fragments,
   tracking parameters and trailing slashes. A page with more than
   `+SCRAPE_AND_PROCESS__MAX_LINKS_PER_DOCUMENTATION+` links (a site map) is
   saved, but its links are not followed. Dropped are links already scraped or
   decided, links whose path segment matches a forbidden part (login, pricing,
   changelogs, non-English locales, …) and links outside the *crawl scope*:
   * the hosts of the starter links, and with a lower rank the other hosts of
     the same site (`community.example.com` next to `docs.example.com`), whose
     pages still have to pass the assessment;
   * on shared hosting (`vendor.github.io`, `acme.atlassian.net`,
     `*.readthedocs.io`, …) only the exact host, and on GitHub only the owner of
     the starter repository (`github.com/<owner>/`).
   Links under the path of a starter link and links whose text or URL names IDM
   topics (users, groups, roles, authentication, API reference, SCIM, OpenAPI)
   rank first.
5. *Select* the links to follow with an LLM (`Scrape:Links:Select`), which
   reads all candidate links of the iteration with their link texts in batches
   of `+SCRAPE_AND_PROCESS__MAX_LINKS_PER_ASSESSMENT+` and returns the indices of
   those to follow; a failed batch is recorded in the job `errors`. Page
   assessments and link selections run concurrently, at most
   `+SCRAPE_AND_PROCESS__MAX_CONCURRENT_PAGE_ASSESSMENTS+` at a time. The
   selected links are the next iteration of the scraper loop, which runs up to
   `+SCRAPE_AND_PROCESS__MAX_SCRAPER_ITERATIONS+` (default 4) iterations. Links
   found on the last iteration are never scraped, so they are not sent to the
   LLM; they only decide between the finish reasons `max-iterations-reached`
   (in-scope links remain) and `no-more-links`.
   Robots.txt denials and permanent 4xx responses are not retried; 408, 425,
   429 and server errors are.
6. As each document is saved, it is *chunked* into pieces of at most
   `+SCRAPE_AND_PROCESS__CHUNK_LENGTH+` tokens:
   * An OpenAPI 3 or Swagger 2 description that fits into one chunk stays
     whole. A larger one is split by resource (the first tag of an operation,
     else the first resource segment of its path), and every chunk is itself
     a valid description: the overview chunk holds `info`, servers, security
     schemes and the tag list; a resource chunk holds the operations of one or
     more resources under a short header (title, version, servers) with every
     component they reference, directly or transitively; components no
     operation references get chunks of their own. A resource that does not
     fit is split by path, then by operation, and a component larger than a
     chunk into valid fragments. Chunks keep the syntax and style of the
     source (YAML, indented or minified JSON).
   * SCIM schemas and JSON Schema documents are split into valid JSON
     sub-schemas.
   * Any other document is split by tokens.
7. Each chunk is *processed by an LLM* (`src/documents/processing/`):
   summarized, categorized (`spec_json`, `reference_api`, `tutorial`, …),
   tagged, and annotated with metadata, including `retrieval` (starter link,
   link depth, page assessment, recognized specification and its canonical
   hash, see link:../sessions-and-jobs.adoc#chunk-metadata[chunk metadata]).
   The object classes a chunk documents are added to its `tags`: a class the
   LLM names (the classes the page assessment found on the page are a hint in
   the prompt) only when its evidence contains the class name and appears in the chunk,
   as a whole or through a schema name or path in it (`UserModel`,
   `/api/v3/users`), and for a chunk of an API description also its resources
   and schemas. For such
   a chunk the category (`spec_json` or `spec_yaml`) and the endpoint count
   come from the description, not from the LLM.
8. Processed chunks are persisted as `documentation_chunks` rows with
   `source='scraper'`.

Uploaded files (see link:../sessions-and-jobs.adoc[Sessions and jobs]) go
through the LLM processing and persistence of steps 7–8 with
`source='upload'`; they are split by tokens, except preserved SQL/SCIM schemas
over the single-schema budget, which are split into structurally valid
sub-schemas. Conndev uploads skip the chunk-processing LLM: their binding is
classified deterministically.

== Pitfalls

NOTE: Scraping is the slowest and most fragile stage: it depends on the target
site's structure, anti-bot measures, and the LLM link filtering. If you
already have good documentation (an OpenAPI spec, an exported doc bundle),
uploading it directly to the session is faster and more reliable than
scraping.

NOTE: The scrape targets the first concrete version of `applicationVersion` and
the session's `discoveryInput.applicationVersion` (midPoint always requests
`latest` and names the version only in discovery). It is fixed when the job is
scheduled and stored in the job input as `effectiveApplicationVersion`, so a
scrape of another version never reuses this one. With no concrete version
(`latest`, `current`) the version is not assessed. The application name and
this version are passed to the assessment, link selection and chunk processing
prompts.

NOTE: When a site keeps its content outside `article`/`main`, add its
container to `+SCRAPE_AND_PROCESS__MAIN_CONTENT_SELECTORS+` (CSS selectors,
validated at startup). Without a match the page body is used, which still
excludes header, footer and sidebars.

WARNING: The forbidden-URL list (`+SCRAPE_AND_PROCESS__FORBIDDEN_URL_PARTS+`)
filters out many locale prefixes (`de`, `fr`, `es`, …). An entry matches a whole
URL path segment or file name (`/de/` or `/docs/de`, not `/developer`). If the
documentation you need lives under such a path, adjust the setting.

== Related settings

`+SCRAPE_AND_PROCESS__*+` — scraper loop bounds, main-content selectors, data
file and referenced-spec limits, chunking, concurrency, retry behavior, chunk
categories. See link:../configuration.adoc[Configuration] and
`src/config/scrape.py` for the full list.
