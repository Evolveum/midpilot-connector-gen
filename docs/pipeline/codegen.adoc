= Codegen
:toc: left

link:index.adoc[← Pipeline overview] | link:../index.adoc[Documentation index]

Codegen generates declarative YAML or Groovy code for the midPoint connector, one operation at
a time, from the API model extracted by the link:digester.adoc[digester] plus
the relevant documentation chunks.

Module: `src/modules/codegen/`

== Endpoints

All paths are prefixed with `/api/v1/codegen` and follow the
link:../sessions-and-jobs.adoc[job pattern] (`POST` enqueue, `GET` poll,
`PUT` overwrite the stored code manually).

[cols="2,3", options="header"]
|===
| Resource | Generates

| `/{sessionId}/authorization`
| Authentication/authorization setup code, based on the digester `auth`
  output and the preferred authorization methods.

| `/{sessionId}/classes/{objectClass}/native-schema`
| The native schema definition for one object class, including its ConnId
  attribute mapping (`UID` / `NAME`). Both live in the same artifact
  (declarative YAML or Groovy).

| `/{sessionId}/classes/{objectClass}/search/{intent}`
| Search operation; `intent` is `all` (list all), `filter` (query by
  attribute), or `id` (lookup by identifier).

| `/{sessionId}/classes/{objectClass}/create` +
  `/{sessionId}/classes/{objectClass}/update` +
  `/{sessionId}/classes/{objectClass}/delete`
| The CRUD operations.

| `/{sessionId}/relations/{relationName}`
| Code for one extracted relation (e.g. group membership handling).

| `/{sessionId}/classes/{objectClass}/fix`
| Fixes all generated CRUD, search and native-schema scripts of one object class
  from midPoint runtime errors. `POST` enqueues and `GET` polls.
|===

== How generation works

See link:codegen-references.adoc[Reference documentation] for the operation/protocol
registry and manual update instructions.

1. *Context assembly* — for each operation, `selection/` gathers the digester
   outputs (attributes, auth, and endpoints where available) and the chunks
   recorded as relevant for the operation's result key, plus required midPoint
   connector-development reference material (`selection/docs_loader.py`),
   including the bundled declarative-YAML reference for the resolved protocol
   (`OperationAssets.declarative_docs_path` in `selection/protocol_selectors.py`
   — a shared REST/SCIM reference and a separate SQL one). SQL CRUD/search
   generation requires attributes but not endpoints.
2. *Protocol-specific prompts* — prompts live under `prompts/`, split by
   protocol (`rest/`, `scim/`, `sql/`) and operation. Every operation prompt
   splices in the shared YAML-vs-Groovy policy
   (`prompts/declarative_format_prompts.py`): the LLM prefers declarative YAML
   whenever the bundled reference documents it as sufficient, and falls back to
   Groovy — or YAML with the documented scripting hooks embedded — only where
   the reference shows Groovy is required. The protocol is chosen
   by the effective link:../api-type.adoc[apiType]; SCIM additionally injects
   a shared SCIM context so generated code follows the fixed SCIM baseline
   contracts. The connection target is read per protocol: REST and SCIM get the
   base API URL, SQL gets `databaseName` and no URL at all.
3. *Generation and validation* — the LLM output goes through post-processing
   and format-aware validation (`utils/connector_code_validation.py`, which
   detects YAML vs. Groovy and checks known YAML fields with strict types plus the existing
   Groovy parser for documented script fields; `utils/postprocess.py`). Unknown nested
   YAML options are preserved and logged as `[Codegen:Validation]` warnings, not job
   errors: the connector runtime may support options missing from the local model.
   Their values and scripts are not validated locally. Unknown root keys, malformed
   structures, duplicate keys and invalid known scripts still block acceptance. Worker
   validation runs in a thread without executing the embedded code. New generation
   sends an empty `<result>` until the first valid artifact is accepted; subsequent
   chunks receive that artifact. Invalid responses leave the previous result intact;
   the next chunk also receives the rejected draft and its local validation errors.
   Warnings are sent as advisory feedback about the accepted artifact: the model checks
   them against the framework reference instead of blindly deleting unknown options.
   Feedback contains only the latest candidate and diagnostics, not the history of drafts.
   Empty responses and failed calls retain pending feedback. Identical candidates reuse
   their validation report within the generation, avoiding repeated parsing and warning logs.
   A repair starts with `currentScript` and preserves its format according to the
   repair instructions (`repair.py`, `prompts/repair_prompts.py`).
   After the chunks, unresolved errors *or warnings* trigger at most one final validation
   repair pass, using the existing operation context and the problematic candidate's source
   chunk. This final repair is always enabled when diagnostics remain and is not configurable.
   Transport retries still follow the shared `LLM__*`
   retry settings. A clean generation adds no repair call. Single-pass native-schema
   generation and the object-class fix do not use this mechanism.
   The repair does not count as another processed document. Invalid or empty repair output
   preserves the last accepted artifact; with none, the existing empty-generation or
   original-`currentScript` outcome applies. Infrastructure outages still fail the job.
   Historical job errors remain visible even after recovery, which is recorded in the logs.
   Warnings never become job errors and do not block acceptance.
   The usual format-specific cleanup runs after repair, validates changed output and falls
   back to the accepted artifact if cleanup fails. Validation checks local structure and
   syntax only; it does not execute scripts or prove connector runtime behavior.
4. The final artifact is persisted in the session under the operation's result
   key as `{"format": "YAML", "code": "..."}` or
   `{"format": "GROOVY", "code": "..."}`. Format detection uses the final accepted
   code without an additional LLM call. YAML containing embedded Groovy remains
   `YAML`, because the whole artifact must be loaded as YAML.

=== Code result contract

All code-generation status endpoints retain the existing job envelope, including
`jobId`, `status`, `progress`, `errors`, and `result`. For a finished generation,
the `result` payload contains:

[source,json]
----
{
  "format": "YAML",
  "code": "objectClasses: {user: {create: {enabled: true}}}"
}
----

`format` is always present: `YAML` or `GROOVY` for code, and JSON `null` when no
code was accepted. The `code` field remains a string. For an empty generation,
`result` is `{"format": null, "code": ""}` and the existing `errors` array explains
the outcome. YAML `{}` is a nonempty valid artifact and has format `YAML`.

For SQL and SCIM CRUD/search generation, recognized empty default artifacts are
normalized before validation, including after cleanup. The result names the target
object class and operation and explains that the framework defaults apply:

[source,yaml]
----
# No changes needed. Use framework defaults.
objectClasses:
  "user":
    create: {}
----

An equivalent empty Groovy artifact keeps Groovy format:

[source,groovy]
----
objectClass("user") {
    create {
        // No changes needed. Use framework defaults.
    }
}
----

This adds no executable handler or extra LLM call. Customizations and comments about
unmet requirements remain intact. Missing model output still follows the failure
contract above; it is never converted into a successful defaults result. Stored
artifacts and manual overrides are not rewritten.

This contract covers authorization, native schema, every search intent, create,
update, delete, and relations. Single-operation repairs report the
format of the returned code, including the original artifact if no repair was accepted.

Object-class fix results retain their existing fields. Each item in `result.scripts`
includes its own format, for example:

[source,json]
----
{
  "operationKey": "userUpdate",
  "sessionKey": "userUpdateOutput",
  "format": "GROOVY",
  "code": "objectClass(\"user\") { update {} }"
}
----

Unchanged scripts also include their format. Manual override requests still accept
`{"code": "..."}`; the server determines and stores the format alongside the validated
code. Override acknowledgements and generation enqueue responses are unchanged.

=== Protocol coverage

[cols="2,1,1,1", options="header"]
|===
| Endpoint | `rest` | `scim` | `sql`

| `native-schema` | yes | yes | yes (SQL context and SQL reference)
| `search/{intent}` | yes | yes | yes
| `create` / `update` / `delete` | yes | yes | yes
| `relations/{relationName}` | Groovy (YAML `relationships` is rejected by the connector) | Groovy, respecting automatic SCIM mappings
| discovery only; scripted relationship overrides are unsupported
| `authorization` | yes | yes | *not supported*
|===

IMPORTANT: `authorization` has no SQL prompt family. Requesting it for a `sql`
session fails with `Unsupported operation/protocol: authorization/sql`, unless
the only preferred authorization is the custom `other` method, which returns a
static scaffold without calling the LLM. Write the database authentication
block by hand for now.

== Fixing a deployed connector

`POST /{sessionId}/classes/{objectClass}/fix` acts on one object class, for the
case the per-operation repair cannot serve: midPoint rejected that object class
and you do not know which of its operations is at fault. `objectClass` is a
required path parameter and must identify a class in `objectClassesOutput`.

1. *Collect* - generated Create, Search All/Filter/ID, Update, Delete and
   NativeSchema scripts are loaded only for the selected object class.
   Authorization, relation scripts, and scripts of all other object classes are
   intentionally outside the fix scope. A class removed from
   `objectClassesOutput` cannot be fixed through this endpoint.
2. *Fix* - all scripts plus the midPoint errors go to the LLM in one call,
   together with the bundled midPoint DSL reference for the operations present.
   The model returns *only* the scripts it changed. Everything it does not
   return is kept byte-identical.
3. *Escalate, at most once* - if the model cannot fix the errors without
   application documentation, it says so and asks a specific question; a second
   pass then adds every session chunk referenced by the selected class's
   `{objectClass}EndpointsOutput` and `{objectClass}AttributesOutput`, plus the
   selected class's own `objectClassesOutput` entity. References are deduplicated
   by chunk ID, but are not ranked or capped separately. Documentation selected
   only for other object classes is never included. The complete prompt remains
   subject to `CODEGEN__FIX_MAX_INPUT_TOKENS`. The typical fix stops after the
   first call. Fixes returned by the first pass are retained unless the second
   pass replaces the same operation.
4. *Validate and persist* - each returned script is parsed before use. An
   invalid script, one naming an operation the connector does not have, or one
   identical to the stored version is dropped and reported in
   `rejectedScripts`; the rest are still applied. If every proposal is unusable
   the job fails rather than reporting a fix that changed nothing.

The request body carries `midpointErrors` and may carry `scripts` - user-edited
Groovy that replaces the stored version as input for this run only. The session
is written only if the fix succeeds, in a single transaction.

The fix never reuses a cached job result. Its only side effect is the
write-back, which lives in the worker, and a cache hit would return a stored
result instead of running the worker at all.

== Pitfalls

IMPORTANT: Codegen inherits everything from the digester. Generating code for
an object class whose attributes were never extracted (or were extracted under
the wrong link:../api-type.adoc[apiType]) fails or produces unusable code.
Complete the digester sequence for the class first — `endpoints` →
`attributes` for REST/SCIM, `attributes` alone for SQL — and run
`authorization` before operations that need authenticated calls.

NOTE: Protocol-specific generation endpoints accept an `apiType` query
parameter that overrides the detected protocol for that request. Relation
generation is protocol-independent and does not accept the override. Because the
ConnId mapping is part of `native-schema`, that endpoint's `apiType` override
governs it too.

NOTE: Generated code is stored per operation and can be regenerated or
manually replaced (`PUT`) independently — you do not need to redo the whole
class after fixing one operation. When you know which operation is broken,
prefer the per-operation repair (`currentScript` + `midpointErrors` on that
operation's `POST`) over the object-class fix.

== Related settings

Per-operation generation is driven by the shared `+LLM__*+` settings (model,
retries, timeouts). The object-class fix additionally uses the safe
`CodegenSettings.fix_max_input_tokens` source default of 120,000 estimated
tokens. The check covers the complete rendered input of each LLM pass, including
scripts, errors, DSL references, and escalated documentation. Inputs above it
are rejected, not truncated. See link:../configuration.adoc[Configuration].
