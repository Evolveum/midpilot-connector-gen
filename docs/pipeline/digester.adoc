= Digester
:toc: left

link:index.adoc[← Pipeline overview] | link:../index.adoc[Documentation index]

The digester turns the documentation chunks stored in the session into a
structured model of the target API: metadata, authentication, object classes,
endpoints, attributes and relations. Everything the
link:codegen.adoc[codegen] stage generates is built on these outputs.

NOTE: Relation extraction is a multi-stage pipeline with its own internal
diagnostic output; it has a separate page —
link:relations.adoc[Relation analysis].

Module: `src/modules/digester/`

== Endpoints

All paths are prefixed with `/api/digester`. Each resource follows the
link:../sessions-and-jobs.adoc[job pattern]: `POST` enqueues extraction,
`GET` polls status/result, `PUT` overwrites the stored result manually.

[cols="2,3", options="header"]
|===
| Resource | Purpose

| `/{sessionId}/metadata`
| Application/API metadata — most importantly the detected
  link:../api-type.adoc[`apiType`] and its connectivity target (REST/SCIM base
  URL or SQL database name). *Run this first unless metadata is supplied
  manually.*

| `/{sessionId}/auth`
| Supported authentication methods (API key, OAuth2, basic, …).

| `/{sessionId}/classes`
| Object classes (User, Group, …) with confidence ranking
  (high/medium/low). Accepts `apiType` and <<object-class-intent,`intent`>> query
  overrides.

| `/{sessionId}/classes/{objectClass}/endpoints`
| CRUD/search endpoints for one object class.

| `/{sessionId}/classes/{objectClass}/attributes`
| Attribute schema for one object class.

| `/{sessionId}/relations`
| Relations between object classes (e.g. user–group membership). Accepts an
  `apiType` query override. The staged pipeline behind it and its two outputs
  are described in link:relations.adoc[Relation analysis].

| `/{sessionId}/connectivity-endpoint`
| A cheap endpoint suitable for a connection test.
|===

== How extraction works

1. *Chunk selection* — `selection/` picks the relevant subset of the
   session's documentation chunks per extraction type (criteria over chunk
   categories, `src/documents/filtering/`), so the LLM never sees the whole
   corpus.
2. *Protocol-specific extractors* — the worker layer under `extractors/` is
   split by protocol: `rest/`, `scim/`, `sql/`, chosen by the effective
   link:../api-type.adoc[apiType]. REST derives everything from prose; SCIM and
   SQL start from a deterministic contract and use focused LLM stages where
   interpretation or vendor-specific mappings are required. Relation detection
   always retains the full harvest/sweep/focus/adjudicate/verify LLM pipeline.
3. *Sequence-based extraction* — for large prose-based extractions (including
   REST attributes and shared auth extraction), the LLM returns start/end
   *markers* into the source text; the actual content is then located by fuzzy
   matching in a process pool (`src/core/pool.py`) rather than being
   re-generated by the LLM. Tolerances are configurable
   (`fuzzy_*_marker_error_ratio`, `sequence_max_length`).
4. *Aggregation* — per-chunk results are merged, deduplicated, and
   confidence-ranked across documents (`aggregation/`). Low-evidence metadata
   values are dropped (`info_metadata_uncertainty_threshold`).

Progress of the multi-phase jobs is reported through `JobStage` values
(discovery, deduplication, building, sorting, …).

=== What each step does per protocol

[cols="1,2,2,2", options="header"]
|===
| Step | `rest` | `scim` | `sql`

| `classes`
| Per-chunk LLM extraction from the documentation.
| Standard SCIM baseline classes plus classes found in the session's conndev
  contracts.
| Every table in the schema becomes a candidate, whether it came from a conndev
  SQL export or from a raw `CREATE TABLE` / JSON schema. Nothing is discovered
  by an LLM: an object class of a database connector is always backed by a
  table.
| `endpoints`
| CRUD/search endpoints extracted from the documentation.
| Deterministically pre-generated from the SCIM resource bindings.
| Not applicable — a database connector has no endpoints. The request is
  rejected with `endpoint_extraction_not_supported`; the table each attribute
  maps to comes from `attributes` instead.
| `attributes`
| Marker-based LLM extraction from the relevant chunks.
| SCIM schema attributes merged with documented mappings.
| Columns of the object class's tables — deterministic, no LLM. Each attribute
  records its `databaseCatalog`, `databaseSchema`, `table` and `column` when
  supplied; known primary-key and foreign-key metadata is preserved as
  `primaryKey` and `foreignKey`. Types come from the ConnId types in a conndev
  object-class export, or from the native SQL types in a conndev SQL-table
  export or raw schema.
| `relations`
| REST-focused staged LLM analysis over schema references, properties,
  endpoints, and prose.
| SCIM-focused staged LLM analysis over reference metadata, ResourceTypes,
  vendor mappings, examples, and prose. Custom application attributes remain
  separate from SCIM wire paths. A complex reference is represented by its
  parent relation attribute (`groups`, `members`, `manager`) while the complete
  wire path (`groups.$ref`, `members.$ref`, `manager.$ref`) remains in
  `relationsAnalysisOutput.scimEvidence`.
| SQL-focused staged LLM analysis over DDL, foreign keys, composite keys,
  junction tables, logical mappings, and narrative model documentation.
| `auth`
| Documented authentication methods.
| Documented authentication methods.
| Same documentation-based extraction; it has no database-specific handling.
| `connectivity-endpoint`
| A cheap endpoint for a connection test.
| A cheap endpoint for a connection test.
| No SQL-specific implementation. The shared HTTP-oriented extractor is not
  rejected, but SQL has no base API URL and codegen does not consume this
  output, so skip it for the normal SQL flow.
|===

Object classes always end up ordered the same way regardless of protocol: an
LLM assigns a confidence level (`high`/`medium`/`low`) for the requested
<<object-class-intent,intent>>, the high bucket is then ordered by importance
and the rest alphabetically (`aggregation/object_class_ranking.py`). The most
useful classes are therefore first in the response — for a 200-table database
schema this ranking, not a name heuristic, is what separates `m_user` from
`qrtz_fired_triggers`.

[[object-class-intent]]
=== Object-class intent (`management` / `itsm` / `management_itsm`)

`classes` accepts an optional `intent` query override
(`GenerationIntent` in `src/shared/enums.py`) that changes what counts as a
*primary* object class, without changing which documentation is read:

[cols="1,3", options="header"]
|===
| Value | Prioritizes

| `management` (default)
| IGA/IDM entities — users, groups/teams, organizations/tenants,
  roles/entitlements, memberships/assignments.

| `itsm`
| Service-management work items — tickets/issues/cases, incidents, problems,
  changes, work packages, the queues/projects that contain them, and their
  workflow/status.

| `management_itsm`
| Both sets are primary. Identity/access classes and service-management work
  items receive high confidence; management classes are ordered first within
  the shared high-confidence bucket.
|===

[cols="1,1,1", options="header"]
|===
| Intent | `User` confidence | `WorkPackage` confidence

| `management`
| `high`
| `low`

| `itsm`
| `low`
| `high`

| `management_itsm`
| `high`
| `high`

| Omitted
| `high` (defaults to `management`)
| `low` (defaults to `management`)
|===

Intent affects two stages only, both per-protocol REST/SCIM/SQL:

* *Extraction* (REST/SCIM) — the "what to extract" bucket list is
  intent-specific, but `itsm` extraction still finds identity/management
  classes when they are needed to understand relationships or the API; it
  just does not treat them as the primary target. SQL extraction is
  unaffected — every table is already a candidate regardless of intent.
* *Confidence + ranking* (all protocols, `aggregation/object_class_ranking.py`)
  — this is where prioritization actually happens. A class central to the
  other intent is not dropped, it is ranked `low`: an identity class like
  `User` or `Organization` is `high` under `management` and `low` under
  `itsm`, and a work-item class like `Ticket` or `WorkPackage` is the reverse.
  Under `management_itsm`, a class that is core to either domain is `high`;
  management classes are sorted before ITSM classes within that bucket.

Each intent's wording is centralized in one place
(`prompts/object_class_intents.py`) as a `GenerationIntent -> profile`
registry, so extraction and ranking prompts pick only the relevant intent's
section rather than sending both intents' vocabulary on every call, and a
future intent adds one profile entry instead of a parallel prompt set. The
combined profile is explicit rather than a concatenation of the single-domain
profiles, because their low-confidence rules intentionally contradict each
other.

There is no session-level "remembered" intent: omitting `intent` on a given
`classes` call always resolves to `management`, including for jobs and
sessions that existed before this parameter was added. If a session should be
re-extracted under `itsm` or the combined mode, pass `intent=itsm` or
`intent=management_itsm` (and `skipCache=true`, since a previous result is
cached under the input it was produced with) on that call. Do not send
`management+itsm`; a literal plus sign is ambiguous in URL query strings.

SQL keeps those final semantics but uses a compact LLM contract
(`prompts/sql/object_class_ranking_prompts.py`):

* Confidence input contains only each exact name and a table description with
  at most four sample columns; the LLM returns only `name` and `confidence`.
* Only the high-confidence bucket is LLM-sorted. Its input again contains just
  `name` and the compact description, and its output is an ordered list of
  names. Medium and low buckets are sorted alphabetically without another LLM
  call.
* After ordering, the service rebuilds the response from the original
  candidates, preserving the normal description, structural fields, and
  relevant-documentation references. REST and SCIM keep their existing prompt
  contracts and the public object-class response is unchanged.

This reduces prompt and response tokens for wide schemas, but deliberately
does not remove table candidates: every distinct table still receives a
confidence assignment and appears in the final response.

[[sql-schema-sources]]
=== SQL sources of schema

Three documentation shapes drive the SQL branch and they are not equivalent:

[cols="1,3", options="header"]
|===
| Source | What it provides

| conndev SQL object-class export (`ri:conndev_sql`, see
  link:../api-type.adoc#conndev-exports[API type])
| Authoritative: object-class name, table name, database schema, every column
  with its ConnId type and the `required` / `creatable` / `updateable` flags
  midPoint exported. No LLM is asked to discover object classes.

| conndev SQL-table export (`tableContent`)
| Physical table and column names, native SQL types, nullability, primary keys,
  generated columns, and exact foreign-key constraint names and targets. The
  serialized `tableContent` identity must match its outer document metadata.

| Raw database schema (`CREATE TABLE` DDL or a JSON table list)
| Table and column names, native SQL types, `NOT NULL`, primary keys, and
  table-level foreign-key definitions — but no object-class names and no
  curation of which tables matter. Foreign keys are not promoted automatically
  to digester relations. This is the lowest-precedence physical source: it
  loses to a conndev SQL-table export for any field both describe.
|===

Object-class *names* follow the source. A conndev export states the name
midPoint uses and it is taken verbatim — a table exported as `m_user` becomes
the object class `m_user`, and the generated code declares
`objectClass("m_user")`. A raw schema carries no such name, so it is derived
from the table (`app_users` -> `AppUser`).

When a conndev object-class export and a conndev SQL-table export or raw schema
declare the same physical table and column, they are enriched independently of
upload order. A table is identified by its normalized catalog, schema and table
name; a missing component may match only when there is one compatible candidate.
Known different schemas or catalogs never merge. The object-class export keeps
the logical object-class/attribute names and ConnID capability flags, while the
table schema supplies only the recognized SQL types and physical constraints.
When both a conndev SQL-table export and a raw schema describe the same physical
table, the SQL-table export is authoritative for SQL types, nullability, keys
and constraint names; the raw schema only supplies metadata it alone provides.
Composite foreign keys remain grouped by their constraint name at table level
when the source supplies one; each attribute carries its exact referenced table
and column for downstream generation.

If the identity is contradictory or under-specified for more than one candidate,
the SQL extraction job fails instead of guessing. Distinct conndev object-class
names remain authoritative. If the same public object-class name refers to
multiple physical tables, `/classes` qualifies each colliding name with its
physical catalog/schema/table identity (for example `database1.schema_a.users`).
The GUI sends that exact value back as the object-class routing key. Attribute
extraction preserves `databaseCatalog`, `databaseSchema`, `table` and `column`,
so native-schema and operation codegen keep the same physical identity.

IMPORTANT: A conndev SQL *object-class* export alone does *not* carry primary
keys, foreign keys or nullability. When a matching conndev SQL-table export is
uploaded, those values enrich the attributes; a raw schema can provide the
same class of metadata. Without either table source, `primaryKey` remains
unknown and `mandatory` is set only for columns marked `required`. Parsed
foreign keys are not converted heuristically into `relationsOutput`; the SQL
relation LLM profile confirms them against logical object-class semantics and
preserves physical bindings in `relationsAnalysisOutput`. Review ambiguous
associations before codegen, especially when the DDL has no comments or
logical-name mapping.

== Order matters

IMPORTANT: The link:../api-type.adoc[apiType] must be known before anything
else — either detected by `metadata` or declared with
`PUT /api/digester/{sessionId}/metadata`. Object classes, endpoints, attributes
and protocol-specific codegen steps resolve their protocol from it. Without it
the service falls back to REST, which produces garbage for SCIM or SQL targets.

The intended order within the digester:
`metadata` → `auth` → `classes` → per class `endpoints` → per class
`attributes` → `relations` / `connectivity-endpoint`. Endpoints and
attributes require object classes to exist (jobs fail with
`ObjectClassesNotFoundError` otherwise); relations build on extracted
classes/attributes.

For a `sql` session the order is shorter: `classes` → per class `attributes` →
`relations`.
`endpoints` is skipped entirely — it is rejected for a SQL session, and codegen
does not require it, because each extracted attribute already carries the table
identity and column it maps to. Relation analysis reads SQL documentation
through its own prompt profile and never requires endpoints. The shared `auth`
and `connectivity-endpoint` routes are not SQL-aware and are not part of this
normal path.

== Pitfalls

IMPORTANT: A wrong or missing `apiType` is the most common cause of bad
digester output — see link:../api-type.adoc[API type] for detection details
and the per-request `apiType` query override.

NOTE: Results are cached by input for `+DIGESTER__DIGESTER_INPUT_CHECK_INTERVAL+`
(default 4 weeks); use `skipCache=true` when re-running after prompt or
documentation changes.

NOTE: Auth extraction switches to extended selection criteria when the session
has fewer than `+DIGESTER__AUTH_MIN_DOCUMENTATION_ITEMS+` (default 15)
documentation items — tiny documentation sets behave differently by design.

NOTE: Any result can be corrected manually via `PUT` before moving on —
fixing an object class list by hand is often cheaper than tuning the
extraction.

NOTE: An empty `{"attributes": {}}` result is not treated as a failure by the
codegen guard, which only checks that the result exists. Check the attribute
count before generating: for SQL it usually means the schema source was not
recognized, and the generated operations will be empty scaffolds.
